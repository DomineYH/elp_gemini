# ELP Gemini 프로젝트 헌장

## 핵심 원칙 (Core Principles)

### I. 파일 길이 제한 (File Length Constraint)

**원칙**: 한 파일은 300 라인을 초과하지 않도록 분할하여 모듈성을
높입니다.

**근거**:
- 작은 단위의 변경은 코드 리뷰 효율을 극대화합니다
- 파일이 작을수록 이해하기 쉽고 테스트하기 용이합니다
- 모듈 간 결합도를 낮추고 응집도를 높입니다
- 병렬 개발 시 충돌을 최소화합니다

**적용 기준**:
- 모든 소스 코드 파일에 적용 (`.py`, `.js`, `.ts` 등)
- 테스트 파일도 동일한 제한 적용
- 문서 파일(`.md`)은 예외이나 적절한 섹션 분리 권장
- 자동 생성 파일(migration, schema dump)은 예외

**위반 시 조치**:
- 300 라인 초과 시 파일 분할 계획 수립 필수
- PR 리뷰에서 파일 길이 검증
- 정당한 사유가 있을 경우 Complexity Tracking에 문서화

### II. 라인 길이 제한 (Line Length Constraint)

**원칙**: 한 줄은 80 자를 넘기지 않습니다.

**근거**:
- 80 컬럼 규격은 가독성과 diff 품질을 유지하기 위한 전통적이고
  실용적인 기준입니다
- 코드 리뷰 도구와 터미널 환경에서 최적의 가독성 제공
- side-by-side diff 비교 시 스크롤 없이 확인 가능
- 중첩이 깊어지는 것을 자연스럽게 방지하여 복잡도 감소

**적용 기준**:
- 모든 코드 라인에 적용
- 주석과 문서 문자열(docstring)도 포함
- URL이나 긴 문자열 리터럴은 예외 인정 가능
- linter/formatter 설정에서 자동 검증

**위반 시 조치**:
- 자동 포맷터(black, prettier 등) 설정으로 강제
- CI/CD 파이프라인에서 검증
- 정당한 예외 사유는 인라인 주석으로 설명

### III. 테스트 주도 개발 (TDD - Test-Driven Development)
[비타협적 원칙]

**원칙**: 구현 전 실패하는 테스트를 먼저 작성하고, 모든 테스트가
통과할 때까지 코드를 수정합니다.

**근거**:
- 리팩터링 안전성을 높이고 품질을 향상합니다
- 요구사항을 코드보다 먼저 명확히 합니다
- 테스트 가능한 설계를 자연스럽게 유도합니다
- 회귀 버그(regression bug) 방지
- 문서화 역할을 동시에 수행합니다

**TDD 사이클 (Red-Green-Refactor)**:
1. **Red**: 실패하는 테스트 작성 (요구사항 정의)
2. **Green**: 테스트를 통과하는 최소한의 코드 작성
3. **Refactor**: 통과한 코드를 개선 (테스트는 계속 통과)

**적용 기준**:
- 모든 새로운 기능 개발에 필수
- 버그 수정 시: 버그를 재현하는 테스트 먼저 작성
- 계약 테스트(contract test): 새로운 라이브러리, API 계약 변경 시
- 통합 테스트(integration test): 서비스 간 통신, 공유 스키마 변경 시
- 사용자 스토리별 독립적인 테스트 작성

**예외 상황**:
- 프로토타입이나 탐색적 코딩 (단, 프로덕션 전 테스트 필수)
- UI 레이아웃 초안 (단, 인터랙션 로직은 테스트 필요)
- 일회성 데이터 마이그레이션 스크립트

**검증 방법**:
- PR 제출 시 테스트 커버리지 확인
- tasks.md에서 테스트 태스크가 구현 태스크보다 선행
- CI/CD에서 테스트 실패 시 배포 차단

## 개발 워크플로우 (Development Workflow)

### 기능 개발 프로세스

1. **명세 작성** (`/speckit.specify`):
   - 사용자 시나리오와 인수 테스트 정의
   - 우선순위별 사용자 스토리 작성 (P1, P2, P3...)
   - 각 스토리는 독립적으로 테스트 가능해야 함

2. **구현 계획** (`/speckit.plan`):
   - 기술 스택과 아키텍처 결정
   - Constitution Check 통과 확인
   - 복잡도 위반 시 정당화 문서화

3. **태스크 생성** (`/speckit.tasks`):
   - 사용자 스토리별로 태스크 그룹화
   - 테스트 태스크를 구현 태스크보다 먼저 배치
   - 병렬 실행 가능 태스크 [P] 표시

4. **구현 실행** (`/speckit.implement`):
   - TDD 사이클 준수: Red → Green → Refactor
   - 각 사용자 스토리를 독립적으로 완성 및 검증
   - 체크포인트마다 독립 테스트 실행

### 브랜치 전략

- Feature 브랜치: `###-feature-name` 형식
- 각 사용자 스토리는 독립적으로 배포 가능
- 메인 브랜치는 항상 배포 가능한 상태 유지

### 코드 리뷰 요구사항

- 모든 PR은 헌장 준수 여부 검증
- 파일 길이 (≤300 라인) 확인
- 라인 길이 (≤80 자) 확인
- 테스트 커버리지 확인
- TDD 사이클 증거 확인 (git history의 test-first commit)

## 품질 보증 (Quality Assurance)

### 테스트 계층

1. **단위 테스트 (Unit Test)**:
   - 개별 함수/클래스의 동작 검증
   - 빠른 실행 (< 1ms per test)
   - 외부 의존성 모킹(mocking)

2. **계약 테스트 (Contract Test)**:
   - API 엔드포인트, 라이브러리 인터페이스 검증
   - 계약 변경 시 자동 감지
   - 하위 호환성 보장

3. **통합 테스트 (Integration Test)**:
   - 컴포넌트 간 상호작용 검증
   - 실제 데이터베이스/외부 서비스 사용
   - 사용자 여정(user journey) 시뮬레이션

### 테스트 커버리지 목표

- 단위 테스트: 핵심 비즈니스 로직 80% 이상
- 계약 테스트: 모든 공개 API 100%
- 통합 테스트: 주요 사용자 스토리 100%

### CI/CD 품질 게이트

- 모든 테스트 통과 (필수)
- Linter 검증 통과 (필수)
- 파일/라인 길이 검증 (필수)
- 테스트 커버리지 임계값 달성 (필수)
- 정적 분석 도구 경고 없음 (권장)

## Governance

### 헌장의 권한

이 헌장은 모든 개발 관행보다 우선합니다. 모든 PR과 코드 리뷰는
헌장 준수를 검증해야 합니다.

### 헌장 수정 절차

1. **제안**: 수정 제안서 작성 (배경, 근거, 영향 분석)
2. **검토**: 팀 구성원 리뷰 및 논의
3. **승인**: 합의 도달 시 승인
4. **마이그레이션**: 기존 코드 적용 계획 수립
5. **문서화**: 버전 업데이트 및 변경 이력 기록

### 버전 관리 정책

헌장 버전은 시맨틱 버저닝(Semantic Versioning)을 따릅니다:

- **MAJOR**: 하위 호환 불가능한 원칙 제거 또는 재정의
- **MINOR**: 새로운 원칙/섹션 추가 또는 중대한 확장
- **PATCH**: 명확화, 표현 개선, 오타 수정, 비본질적 개선

### 준수 검토

- 매 PR마다 자동화된 헌장 준수 검증
- 분기별 수동 헌장 준수 감사
- 위반 사항 발견 시 즉시 수정 또는 정당화

### 복잡도 정당화

원칙 위반이 필요한 경우:
1. `plan.md`의 Complexity Tracking 테이블에 문서화
2. 위반 사항, 필요성, 거부된 대안 명시
3. 코드 리뷰에서 검토 및 승인

### 런타임 개발 지침

- 구현 세부사항 및 베스트 프랙티스는 별도 문서 관리
- 기계사제 페르소나 등 프로젝트별 스타일은 `doc/rules.md` 참조
- 헌장은 변하지 않는 원칙, 지침은 진화하는 관행
