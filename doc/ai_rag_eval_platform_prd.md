# AI 기반 문서 평가·QnA 플랫폼 PRD (개념 버전)

## 1. 제품 개요

### 1.1 제품 이름 (가칭)
- **제품명(가칭)**: AI 문서 평가 & QnA 플랫폼  
- **한줄 정의**:  
  사용자가 올린 문서를 대상으로,
  1) 문서 내용에 대해 질의응답(QnA)을 하고  
  2) 사전에 정의된 평가 기준(루브릭/문서 B)을 기준으로 자동 평가 보고서를 생성해 주며,  
  3) 관리자에게는 전체 사용자·문서·QnA·평가 현황을 제공하는  
  **RAG 기반 교육/평가 특화 어플리케이션**.

### 1.2 문제 인식

1. **문서 기반 평가와 피드백의 부담**
   - 학생·연구자·교사·직장인 등은 보고서/과제/논문 등 A 문서를 작성하지만,
   - 이를 평가하거나 피드백하는 작업은 시간과 전문성이 많이 필요함.
2. **AI 활용 QnA의 한계**
   - “PDF를 올려서 질문하는” 기능은 많지만,  
     - 사용자별 데이터 격리,  
     - 평가 기준(문서 B)에 따라 **일관된 평가**를 내리는 기능,  
     - 관리자 수준의 **품질 관리/통계/프롬프트 튜닝**은 미비함.
3. **관리자·운영자의 어려움**
   - 개별 사용자가 AI를 어떻게 사용하는지,  
   - 평가 결과가 어떤 기준으로 생성되는지,  
   - 프롬프트를 바꿨을 때 품질이 어떻게 변하는지 모니터링하기 어려움.

### 1.3 솔루션 개요

본 어플리케이션은 다음을 목표로 한다.

- 사용자는 **자신의 문서 A를 업로드**하고,  
  - 그 문서 내용을 기반으로 **QnA(질문·답변)**를 수행할 수 있으며,
  - 별도의 평가 기준 문서 B 및 프롬프트에 따라 **자동 평가 보고서**를 받을 수 있다.
- 모든 문서·QnA·평가 결과는 **사용자별로 분리**되고,
  - 클라우드 상에서는 RAG(File Search Tool)로만 활용되며
  - 로컬 DB에는 원문과 메타데이터, 보고서가 안전하게 저장된다.
- 관리자는 **대시보드**를 통해
  - 전체 사용자 현황, 문서 업로드 현황,
  - 평가 보고서,
  - 사용자별 QnA 내역(챗봇과의 대화)까지 조회하고,
  - QnA/평가에 사용되는 **시스템 프롬프트를 직접 작성·관리**하면서
  - 서비스 품질을 지속적으로 튜닝할 수 있다.

## 2. 주요 사용자 및 페르소나

### 2.1 일반 사용자 (User)

**예시 페르소나**

- 대학생/대학원생: 과제, 보고서, 논문 초안을 업로드해 피드백 및 평가를 받고 싶음.
- 교사/강사: 학생이 제출한 수업 보고서, 프로젝트 산출물에 대해 자동 평가와 피드백을 얻고 싶음.
- 직장인: 기획서, 보고서, 제안서 초안을 업로드하고, 문서 내용에 대한 QnA 및 개선 방향을 받고 싶음.

**필요/니즈**

- 내가 쓴 문서를 중심으로 **문맥 있는 질의응답**을 하고 싶다.
- **명확한 기준**(루브릭, 예시 문서 등)에 따라 자동 평가/피드백을 받고 싶다.
- 나의 문서·QnA·평가 결과가 **다른 사용자와 섞이지 않고 안전하게 관리**되기를 원한다.

---

### 2.2 관리자 (Admin)

**예시 페르소나**

- 교육 기관의 담당자/연구 책임자:  
  - 여러 교사·학생이 시스템을 사용하는 상황을 **전체적으로 모니터링**하고 싶음.
  - 평가 기준과 프롬프트를 설계/조정하고 싶음.
- 서비스 운영자/PM:  
  - AI 응답 품질을 **로그 단위로 모니터링**하고,  
  - 프롬프트 수정 전/후 차이를 분석하면서 **지속적으로 개선**하고 싶음.

**필요/니즈**

- 사용자별 문서/평가/QnA 현황을 한 눈에 보고 싶다.
- 특정 사용자나 특정 문서의 **상세 QnA 내역**을 확인하고, 문제가 생기면 대응하고 싶다.
- QnA/평가의 **시스템 프롬프트를 코드 수정 없이 대시보드에서 관리**하고 싶다.

## 3. 제품 특징 및 가치 제안

### 3.1 핵심 가치

1. **문서 중심 RAG 서비스**
   - 각 사용자가 올린 문서 A를 기반으로,  
     - QnA와 평가를 모두 RAG 방식으로 수행.
   - Google File Search Tool을 활용해,
     - 문서를 클라우드에서 자동으로 청크/벡터화하고,
     - 사용자의 질의에 대해 해당 문서와 평가 기준 문서 B를 참조하여 답변/평가를 생성.

2. **사용자별 데이터 격리**
   - DB와 메타데이터 설계 및 File Search의 `metadata` 필터링을 통해,
     - 같은 store를 쓰더라도  
       **user_id + random_key**로 문서를 정확히 식별하고  
       다른 사용자 데이터와의 혼합을 방지.
   - 프론트/백엔드 레벨에서 인증된 user_id에 따라 문서 목록, QnA, 평가 결과가 분리되어 표시.

3. **관리자 중심 품질 관리**
   - 관리자 대시보드에서
     - 전체 사용자/문서/평가/QnA 기록을 조회 가능.
   - QnA 및 평가용 시스템 프롬프트를 **버전 단위로 관리**하여,
     - 어떤 버전의 프롬프트가 어떤 QnA/평가에 사용되었는지 추적 가능.
   - 프롬프트 변경 → QnA/평가 로그 분석 → 재조정의 **피드백 루프**를 지원.

4. **교육·평가 도메인에 특화**
   - 단순 “문서 QnA 툴”이 아니라,
     - 문서 B(평가 기준)와 시스템 프롬프트를 활용해 **서술형 평가 보고서**를 생성하는 기능을 내장.
   - 학습/수업/연구 보고서 등 **교육 문서 피드백**에 바로 적용하기 좋은 구조.

## 4. 기능 개요 (무엇을 할 수 있는지)

### 4.1 일반 사용자 기능

1. **문서 A 업로드 및 관리**
   - 문서 업로드
     - 파일(PDF 등)을 업로드하면 시스템이 랜덤 키를 생성하여 로컬에 저장.
     - 해당 문서를 File Search Store(main-store)에 인덱싱.
   - 문서 목록 보기
     - 자신이 업로드한 문서들만 리스트로 확인.
     - 제목, 업로드 시간, 상태(활성/삭제) 등 확인.
   - 문서 삭제(또는 논리 삭제)
     - 더 이상 사용하지 않을 문서를 삭제 요청할 수 있음
     - 실제 File Search store에서 제거하거나, status만 `deleted`로 변경하는 방식은 운영 정책에 따름.

2. **문서 기반 QnA**
   - 특정 문서 A를 선택한 후, 해당 문서를 기반으로 질문을 입력.
   - 시스템은 File Search Tool을 통해
     - `user_id`, `random_key`에 해당하는 청크만 검색하여 RAG 수행.
   - 사용자는
     - 문서 요약, 특정 부분 설명 요청, 내용 비교, 재구성 등 다양한 질의응답 가능.
   - 이전 QnA 내역 확인 (선택)
     - 같은 문서에 대해 과거에 했던 질문/답변 로그를 조회할 수 있음.

3. **문서 자동 평가/보고서 생성**
   - 문서 A를 선택하고, 원하는 평가 템플릿 또는 평가 버튼을 클릭.
   - 시스템은
     - 평가 기준 문서 B (rubric-store),
     - 평가용 시스템 프롬프트,
     - 문서 A의 내용  
     을 결합해 평가 보고서 생성.
   - 결과:
     - 점수/등급,
     - 항목별 피드백,
     - 총평,
     - 개선 제안 등이 포함된 텍스트 보고서.

---

### 4.2 관리자 기능

1. **관리자 로그인 & 권한 관리**
   - 관리자 전용 로그인 화면.
   - 일반 사용자와는 다른 경로/권한으로 서비스 접근.

2. **사용자/문서/평가/QnA 현황 대시보드**
   - 요약 지표:
     - 전체 사용자 수
     - 기간별 업로드 문서 수
     - QnA 호출 횟수
     - 평가 실행 횟수 등
   - 사용자 목록:
     - 각 사용자별 문서 수, 최근 활동 시각 등 표시.
   - 특정 사용자 상세:
     - 해당 사용자의 문서 목록
     - 각 문서에 대한 평가 보고서 리스트
     - 해당 문서에 대한 QnA 로그

3. **QnA 로그 모니터링**
   - `qa_logs` 기반으로
     - 사용자 질문,
     - 모델 답변,
     - 사용된 모델 이름,
     - 사용된 시스템 프롬프트 버전
     등을 열람 가능.
   - 필터:
     - 사용자, 문서, 기간, 모델, 프롬프트 버전 등으로 필터링.

4. **평가 보고서 관리**
   - 전체 평가 실행 목록(Evaluation Runs)을 조회.
   - 특정 실행을 클릭하면
     - 평가 기준 템플릿 이름,
     - 점수/등급,
     - 항목별 피드백, 전체 보고서 내용 확인.

5. **시스템 프롬프트 관리**
   - QnA용, 평가용 프롬프트를 **타입별로 관리**.
   - 새 프롬프트 추가 시
     - 기존 버전은 `is_active=false`로 전환,
     - 새 버전은 `is_active=true`로 설정.
   - 프롬프트 변경 내역 및 버전 기록을 확인해,
     - 특정 시점에 어떤 프롬프트를 썼는지 쉽게 추적 가능.

## 5. 주요 사용자 시나리오

### 5.1 사용자: 문서 업로드 → QnA

1. 사용자 로그인.
2. “문서 업로드” 화면에서 PDF 파일을 업로드, 제목 입력.
3. 시스템이 문서를 저장하고, File Search에 인덱싱.
4. 문서 목록에서 방금 업로드한 문서를 선택.
5. “QnA” 탭으로 이동해 질문 입력:
   - 예: “3장 연구 방법 부분을 간단히 요약해줘.”
6. 시스템이 해당 사용자 + 해당 문서에 해당하는 벡터를 기반으로 RAG 수행.
7. 답변을 화면에 출력, 필요 시 이전 대화 내역을 함께 보여줌.

### 5.2 사용자: 문서 자동 평가(보고서 생성)

1. 문서 목록에서 평가를 원하는 문서 A 선택.
2. “평가/보고서 생성” 버튼 클릭.
3. 특정 평가 템플릿 선택(또는 기본 템플릿).
4. 시스템이
   - 문서 A 내용,
   - 평가 기준 B 문서,
   - 평가용 시스템 프롬프트를 바탕으로
   - 자동 평가 수행.
5. 보고서 결과(점수, 항목별 피드백, 종합 코멘트)를 화면에 표시하고, DB에 저장.

### 5.3 관리자: 전체 서비스 모니터링

1. 관리자 로그인 후 대시보드 진입.
2. 상단 카드에서
   - 오늘 업로드된 문서 수,
   - 최근 7일 QnA 횟수,
   - 평가 실행 횟수 확인.
3. 사용자 목록에서 특정 사용자 선택:
   - 그 사용자의 문서와 평가 결과를 확인.
4. QnA 로그 메뉴에서
   - 최근 24시간 동안의 QnA 내역,
   - 특정 프롬프트 버전이 사용된 QnA만 필터링해 품질 검토.
5. 필요하다면 프롬프트를 수정하고,
   - 새 버전을 활성화해 향후 QnA/평가에 반영.

## 6. 비범위(Out of Scope)

이 PRD는 **“어떤 종류의 어플리케이션인지”에 집중**하고 있으며, 아래 항목은 별도의 스펙 문서에서 정의한다.

- UI/UX 상세 와이어프레임, 화면 설계서
- API 스펙, 요청/응답 포맷, 에러 코드 정의
- 실제 Google Gemini API 호출 예제 코드, SDK 선택(FastAPI, Node 등)
- 배포 아키텍처(클라우드 인프라, CI/CD 등)
- 계정/결제/요금제 관련 정책
- 고급 권한 모델(조직 단위, 역할 기반 세분 권한 등)

## 7. 요약

이 어플리케이션은:

- **“사용자가 올린 문서 A를 중심으로”**
  - QnA와 평가를 제공하는 **문서 중심 RAG 플랫폼**이며,
- **교육/평가 도메인에 최적화**된
  - 평가 기준 문서 B + 시스템 프롬프트 기반의 자동 평가 기능,
- **관리자 관점에서의 가시성과 제어**
  - 사용자/문서/QnA/평가 로그를 모두 한 대시보드에서 관리하고
  - 프롬프트 버전을 운영 레벨에서 튜닝할 수 있는 기능을 제공하는 것이 핵심이다.

이 문서를 기반으로, 다음 단계에서  
- 상세 기능 명세(Spec),  
- API/DB/서비스 아키텍처,  
- 화면 설계서  
등을 별도 문서로 확장하면 된다.
